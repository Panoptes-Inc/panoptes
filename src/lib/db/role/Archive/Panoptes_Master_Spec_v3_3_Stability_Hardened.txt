1. Product Definition
1.1 Panoptesとは何か
Panoptesは、
「競合・業界・自社の構造を読み、戦略を可視化し、実行優先順位まで導く戦略OS」
である。

Panoptesは以下ではない
- トラフィック推定ツール
- アナリティクスツール
- Similarweb系
- SEOツール
- LP改善ツール

Panoptesは以下である
- 構造理解装置
- 因果説明装置
- 戦略提案装置
- 実行優先順位エンジン
- 思考圧縮UI
- 戦略OS

1.2 MVPの目的
- URL入力から、競合・業界・自社の構造分析を実行する
- Internal / Visual の2レイヤーで6軸評価を行う
- 同格比較を軸に競合10社を分析する
- 業界構造を推定する
- 自社の差分と改善余地を示す
- 戦略提案3件を生成する
- 30/60/90日プランを task 管理付きで生成する
- snapshot として保存し、再分析で更新できるようにする

1.3 MVPでやらないこと
- 流入流出推定
- 滞在時間推定
- CVR推定
- 広告チャネル分析
- 指名検索推定
- GA / Search Console 統合
- Panoptes独自タグによる行動収集
- リアルタイム更新
- 自動改善実行
- 実行代行

4.5 Initial Analysis Progress Shell
URL入力後から snapshot 保存完了までの間、中央 white panel を進行UIの唯一の主表示とする。
この UI は route 切替ではなく、同一 shell 内の phase 切替で動く。

4.5.1 中央 panel の役割
- 進行段階の視覚化
- 現在処理中の内容の要約表示
- bootstrap結果の確認
- 修正導線
- 失敗時の復旧導線
- 完了後の dashboard 遷移

4.5.2 進行UIの固定5段階
- step_1: target_scan
  表示文言例: 分析対象URLを分析中です…
- step_2: inference_review
  表示文言例: 業界・構造タイプ自動推定
- step_3: competitor_analysis
  表示文言例: 競合を分析中です…
- step_4: industry_analysis
  表示文言例: 業界構造を分析中です…
- step_5: strategy_synthesis
  表示文言例: 競合×業界×自社の差分を分析中です…

4.5.3 step と backend pipeline の対応
- step_1 = project create + bootstrap crawl + URL正規化 + 初期到達確認
- step_2 = 業界推定 + 構造タイプ推定 + サイト規模推定 + confidence計算 + user confirmation待ち
- step_3 = competitor set construction + competitor analysis crawl + competitor observation bundle
- step_4 = market structure synthesis + type distribution + whitespace extraction
- step_5 = self synthesis + engine calculation + strategy generation + 30/60/90 generation + snapshot commit

4.5.4 auto advance 原則
各段階の完了後、中央 panel は自動的に次段階へ進む。
ただし進行は server-confirmed milestone にのみ従う。
フロントの推測だけで step を進めてはならない。

4.5.5 progress UI 最小表示時間
ちらつき防止のため、各 step は最小 500ms 以上表示してよい。
ただし進行を遅く見せるために 2秒以上の人工遅延を標準化してはならない。
MVPでは「自然に見える最小演出」に留める。

4.5.6 panel 自動移動の実装原則
- panel 自体を unmount / remount しない
- panel 内の content だけを keyed transition で差し替える
- height は step 間で急変させず min-height を固定する
- progress dot / line / title / body / action area を別々に壊さない
- action button の disabled / hidden は phase rule に従って制御する

4.5.7 step_2 の confirm 画面
推定結果確認画面では以下を表示してよい
- 推定業界
- 推定構造タイプ
- 推定サイト規模
- confidence label

使用可能導線
- 修正する
- 戦略分析開始

固定ルール
- confirm前に step_3 へ進めない
- confirm画面表示中は analysis_job を competitor分析まで進めない設計でよい
- 修正内容が保存されるまで次stepへ進めない

4.5.8 step skip 禁止
初回分析では 5段階を UI 上必ず通す。
backend 内部で一部処理が高速完了しても、UI 表示上は段階を飛ばしてはならない。
ただし server 側で複数段階がすでに完了している場合、
フロントは step を順に短時間で consume して現在段階へ追いついてよい。

4.5.9 completion rule
step_5 が完了し snapshot commit が成功した時のみ、
selected_project_id と selected_snapshot_id を更新して通常 dashboard 表示へ遷移してよい。

5.2 UI visible flow
- visible_step_1 = target_scan
- visible_step_2 = inference_review
- visible_step_3 = competitor_analysis
- visible_step_4 = industry_analysis
- visible_step_5 = strategy_synthesis

5.3 phase transition authority
phase 遷移の正は server とする。
フロントは polling または stream で phase を受け取り、単調増加で反映する。

5.4 monotonic progress rule
progress_step は後退してはならない。
受信値が現在 step より古い場合は無視する。
ただし failed / cancelled は例外で、現在stepに対する終端状態として上書きしてよい。

5.5 resume rule
ページ再読み込みや route 再入場時は、
analysis_job の current_phase と current_phase_started_at から UI を復元する。
一時的な local UI state のみを正としてはならない。

6. Crawling Architecture
6.1 クローリング方針
PanoptesはAIクローリングを行わない。
すべてのクロールは機械的クローリングで行う。
クローリングエンジンは Python crawler とする。

6.2 Crawl Modes
- bootstrap crawl
- analysis crawl
- monitoring crawl

6.3 bootstrap crawl
目的
- サイトの基本推定
- 業界
- サイトタイプ
- 構造タイプ
- 競合候補

対象
- top
- navリンク
- footerリンク
- 代表ページ

最大
- 10 pages

6.4 analysis crawl
目的
- 完全分析
- Internal evidence取得
- Visual evidence取得

対象
- 最大30ページ
- 優先: top / pricing / feature / faq / case / contact

6.5 monitoring crawl
目的
- 競合監視
- 差分検知
- Feed生成
- Radar生成

対象
- 主要ページのみ
- 最大10ページ

6.6 URL Discovery Rules
取得対象
- 同一ドメイン
- HTMLページ
- nav / footer / CTA から辿れるページ

除外
- ログイン
- cart
- checkout
- session URL
- PDF
- 画像
- zip
- 外部リンク
- 検索ページ

URL正規化
- tracking削除
- fragment削除
- canonical優先
- duplicate除外
- www / non-www 差分統合
- trailing slash 正規化
- http→https 可能時は https を優先

6.7 Page Type Routing
page_type

- pricing
- feature
- comparison
- faq
- case
- company
- contact
- article
- product
- unknown

- faq

6.9 Visual Observation
Visualは capture → AI理解 の順序で行う。
AIが直接クロールすることは禁止。

取得
- first view screenshot
- full page screenshot

Visual評価対象
- 視覚階層

6.10 Diff Detection
4段階
- Level1 URL差分
- Level2 HTML hash差分
- Level3 構造差分
- Level4 意味差分（AI）

6.11 Crawl Failure Classification
失敗分類を固定する。
- unreachable
- blocked
- timeout
- unsupported_site_shape
- insufficient_pages
- parse_failed
- screenshot_failed_partial
- extraction_failed_partial

原則
- partial failure は即全体失敗にしない
- engine実行に必要な最低 evidence を満たすかで継続可否を判定する
- failure reason は user-facing label に変換して返す

8.4 competitor pool degradation rule
競合候補が不足する場合は、以下の順で緩和する。
1. 構造タイプ一致を優先したまま規模条件を緩和
2. 業界近接カテゴリまで緩和
3. 候補不足であることを明示し、10未満でも実行

selected strategy、phase plans、phase tasks は snapshot に紐づくが、
current strategy state として project にも反映される。
「snapshot由来の推奨プラン」と「現在の実行状態」を分離保持する。

12.5 Project Display State
project は以下の display_state を持つ。

- ready
- creating
- queued
- analyzing
- awaiting_confirmation
- completing
- completed
- failed
- empty

定義
- ready / completed: current_snapshot_id が存在し、表示可能
- queued: analysis_job 作成済み、実行待ち
- analyzing: analysis 実行中
- awaiting_confirmation: 推定確認待ち
- completing: snapshot commit 直前から commit 完了まで
- failed: 最新 analysis が失敗
- empty: project は存在するが snapshot 未生成
- creating: create_project_flow 上の一時状態

UIルール
- ready / completed は通常描画
- queued / analyzing / completing は loading / progress 表示
- awaiting_confirmation は inference review 画面を表示
- failed は error state + retry 導線
- empty は start-analysis empty state を表示

12.6 Project Creation and Selection Safety Rules
以下を固定ルールとする。

- 「+」押下では selected_project_id を変更しない
- create project 成功前に既存 project を unmount しない
- current_snapshot_id = null をエラー扱いしない
- snapshot 未生成 project 選択時は empty state / analyzing state / failed state を表示する
- strategy / industry / self / panoai は has_snapshot に応じて guarded rendering を行う

12.7 UI Guard Rendering Rule
各タブは以下で描画分岐する。

12.7.1 has_snapshot = true
- competitors / industry / self / strategy / panoai を通常描画

12.7.2 has_snapshot = false and latest_job_status in (queued, running)
- analyzing state を表示
- skeleton / progress / 「分析中」表示

12.7.3 has_snapshot = false and latest_job_status = failed
- failed state を表示
- retry 導線
- target_url 再確認導線

12.7.4 has_snapshot = false and latest_job_status is null
- empty state を表示
- 「URLを入力して分析開始」

12.8 Snapshot Commit Safety
snapshot は header / payload / strategy_plan / phase_task を整合状態で commit しなければならない。
途中成功の見かけを禁止する。

固定ルール
- current_snapshot_id 更新は最後に行う
- payload insert 前に current_snapshot_id を更新しない
- commit 成功前に completed を返さない
- commit 途中で失敗した場合は failed または commit_failed を internal に残す
- user-facing では failed として再試行導線を出す

12.9 stale job overwrite prevention
古い job が新しい snapshot を上書きしてはならない。

固定ルール
- analysis_job には started_at と job_generation を持たせてよい
- project.latest_analysis_job_id と一致しない job は current_snapshot_id を更新してはならない
- reanalysis 開始後、旧job完了通知は UIで無視してよい

12.10 refresh / reconnect recovery
ページ更新・復帰時は DB または analysis_status API を正として current state を復元する。
未保存 local animation state は復元対象ではない。

16.6 Implementation Notes for Project List and Create Flow
- 「+」は new project modal / drawer の open trigger とする
- 作成成功前に route 遷移しない設計でもよい
- 一覧追加後に toast で
  「分析を開始しました。完了まで他の project を確認できます」
  を表示するとUXが良い
- project list card は常に nullable-safe に描画する

16.7 Initial Progress UI Implementation Notes
- progress polling は 1.5s〜3s の backoff で十分
- hidden tab 中は polling 間隔を伸ばしてよい
- network reconnect 時は即時 progress refetch を行う
- panel transition 中でも polling は止めない
- 新しい phase 受信後は animation queue に積み、表示は単調に進める
- failure 受信時は進行中 animation を打ち切って error view に遷移してよい
- completed 受信後も dashboard payload が未到着なら completing view を表示してよい

16.8 Route / Tab Safety
- analysis 実行中でも他 project / 他 tab 閲覧を禁止しない
- ただし現在 panel の analysis_session_id と一致しないデータで UI を上書きしない
- selected project 変更時は前 project の polling を停止する
- browser back で create flow に戻っても duplicate submit しない

16.9 Offline / Timeout Safety
- 一時的通信断では job を failed 扱いしない
- client timeout と server failure を混同しない
- polling 失敗時は「接続を確認中…」の中間状態を表示してよい
- server が job running を返す限り progress UI を維持する

16.10 Duplicate Trigger Safety
以下を禁止する。
- Enter連打で create-and-start-analysis 多重発火
- confirm button 連打で competitor analysis 多重発火
- reanalyze 多重実行

必要対策
- submit lock
- idempotency_key
- latest_analysis_job_id comparison
- server-side mutex または generation check

16.11 Reanalysis Safety
reanalysis は旧 snapshot を即消さない。
新 snapshot commit 完了まで既存 dashboard を保持する。
失敗時は旧 snapshot を current のまま維持してよい。
