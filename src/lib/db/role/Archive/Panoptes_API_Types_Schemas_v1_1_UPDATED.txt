Panoptes API Types & Schemas Draft v1.1
統合テキスト版（Naming Rule / Strategy-Task Responsibility / View Payload Rule 反映版）

==================================================
0. 固定前提
==================================================

0.1 命名ルール
- DBカラム / API request-response / snapshot payload は snake_case
- アプリ内部の関数名 / 変数名 / utility は camelCase
- Type / Interface 名は PascalCase

つまり、
- 通信と保存は snake_case
- 実装ロジックは camelCase
で統一する。

0.2 strategy と phase task の責務
- strategy = 選択中の戦略テーマ
- phase plan = 30/60/90 の実行管理
- task = 各フェーズ内の具体タスク
- task transition = 状態変更履歴
- reanalysis merge = 再分析時の引き継ぎ判定

この責務は固定し、以後ブレさせない。

0.3 API の返却原則
MVPのAPIは raw engine result を返さない。
返すのは以下のみ。
- job status
- snapshot view payload
- strategy state
- usage state

UIは生の engine 内部構造を直接読まない。
読むのは整形済み payload のみとする。

3. API 設計ルール
==================================================

3.1 API は raw engine result を返さない
返してよいもの:
- analysis job status
- snapshot view payload
- strategy state
- usage state

返してはいけないもの:
- engine の中間計算結果そのまま
- raw submetric bundle
- internal-only benchmark matrix
- confidence calculation internals
- coherence calculation internals
- crawler raw dump

3.2 dashboard API の責務
GET /api/project/:project_id/dashboard は、
UIがそのまま描画可能な SnapshotViewPayload を返す。
フロント側で engine 結果を再計算しない。

3.3 strategy API の責務
- select strategy は「どの戦略を現在戦略として採用したか」を保存する
- update phase task status は task の現在状態だけを更新する
- task transition はサーバ側で自動記録する

3.4 analysis API の責務
- start analysis は job を発行する
- get analysis job は job の進捗のみを返す
- completed 後は dashboard API が current_snapshot_id を基準に payload を返す

3.5 usage API の責務
usage API は組織単位の現在状態を返す。
MVPでは以下を返せば十分。
- total_spu_used
- spu_monthly_limit
- analyses_count
- screenshots_used
- forced_low_mode_active

4. 命名ルール適用メモ
==================================================

4.1 通信と保存
以下は snake_case に統一する。
- API request body
- API response body
- DB columns
- JSONB payload keys
- snapshot payload keys

例:
- project_id
- current_snapshot_id
- selected_strategy_key
- previous_strategy_fit_index
- forced_low_mode_active

4.2 実装ロジック
以下は camelCase に統一する。
- function names
- local variables
- service methods
- utility names

例:
- createProject
- startAnalysisJob
- getProjectDashboard
- updatePhaseTaskStatus
- buildSnapshotViewPayload

4.3 型名
Type / Interface / Schema export 名は PascalCase または lowerCamel + Schema に統一する。
例:
- CreateProjectRequest
- CreateProjectResponse
- SnapshotViewPayload
- createProjectRequestSchema
- getProjectDashboardResponseSchema

==================================================
5. Strategy / Phase Task Responsibility Memo
==================================================

- strategy = 選択中の戦略テーマ
- phase plan = 30/60/90 の実行管理
- task = 各フェーズ内の具体タスク
- task transition = 状態変更履歴
- reanalysis merge = 再分析時の引き継ぎ判定

責務分離ルール:
- strategy は「方針」
- phase plan は「実行単位」
- task は「最小アクション」
- task transition は「履歴」
- reanalysis merge は「前回状態の継承判定」
